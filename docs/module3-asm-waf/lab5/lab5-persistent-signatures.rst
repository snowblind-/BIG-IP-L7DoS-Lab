Lab 5: Custom Persistent DoS Signatures
=======================================

The **Security > DoS Protection > Signatures** screen holds two kinds of DoS
signature. This lab builds and mitigates with the *persistent* kind — including
one you author yourself in the GUI.

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - Kind
     - Description
   * - Dynamic
     - Auto-generated by the Behavioral DoS (BADoS) engine when it detects
       server stress and traffic that deviates from the learned baseline.
       Transient — they age out, and the list is capped (1024 HTTP per object).
   * - Persistent
     - Permanent. Either a dynamic signature promoted with **Make Persistent**,
       or a **user-defined** signature you author from scratch with your own
       predicates. Can be shared across protected objects.

Unlike a Bot signature (Module 1, Lab 5 covers why those can't negate), a
user-defined *persistent DoS* signature **is** hand-authored: you pick the
predicates — ``metric`` / ``operator`` / ``arguments`` — that match the attack.
Notably, ``http.<name>_header_exists eq false`` lets a signature match on a
header being **absent** — the DoS-profile-native counterpart to the Module 1
header-absence iRule.

.. list-table:: Lab environment
   :header-rows: 1
   :widths: 30 30 40

   * - Role
     - Address
     - Notes
   * - Attack client (kali)
     - ``10.1.10.100``
     - Generates the flood
   * - Virtual server
     - ``vs-lab-dos`` — ``10.1.10.63``
     - Runs ``lab_dos_bados_profile`` (behavioral detection)
   * - CLI supplement
     - ``configs/profiles/dos-persistent-signature.conf``
     - Merge-loadable equivalent + promote/approve commands

.. note::

   Persistent signatures are only evaluated when the DoS profile on the VS has
   application-layer request-signature detection enabled. This lab reuses the
   BADoS profile from Lab 2 on ``vs-lab-dos``. If you enable **Use Approved
   Signatures Only** on that profile, *only* signatures whose Approval State is
   ``Manually-approved`` will mitigate — dynamic or persistent alike.

HTTP-family rules to know
-------------------------

The Add Signature form and TMOS enforce these for any ``http`` DoS signature:

.. list-table::
   :header-rows: 1
   :widths: 32 68

   * - Field
     - Allowed for HTTP
   * - Type
     - Persistent (you cannot *create* a dynamic signature)
   * - Deployment State
     - Learn Only or Mitigate
   * - Threshold Mode
     - Manual (detection/mitigation thresholds are 0 — HTTP signatures match on
       predicates, not events-per-second)
   * - Approval State
     - Approved (``Manually-approved``) to mitigate under "use approved only"

Task 1: Author a custom persistent signature (GUI)
--------------------------------------------------

#. Go to **Security > DoS Protection > Signatures** and select the
   **Persistent** tab.

#. Click **Add Signature**. Set **Family** = HTTP and name it
   ``lab_sig_scripted_flood``.

#. Build the **Predicates List** — click **Add**, choose a metric, an operator,
   and a value; repeat to AND several conditions together. For a scripted flood,
   a good starting set is:

   .. list-table::
      :header-rows: 1
      :widths: 40 20 40

      * - Metric
        - Operator
        - Value
      * - ``http.user_agent_header_exists``
        - eq
        - false
      * - ``http.request.method``
        - eq
        - GET
      * - ``http.uri_len``
        - between
        - 0-15

   The builder shows the metrics your version supports. Common HTTP ones:
   the ``*_header_exists`` booleans (``user_agent``, ``referer``, ``accept``,
   ``host``, ``pragma``, ``cache_control``, ``x_forwarded_for``, ``unknown``,
   or any custom header), plus ``http.request.method``, ``http.uri_len``,
   ``http.uri_parameters``, ``http.uri_file``, ``http.accept``,
   ``http.headers_count``, ``http.referer``. Operators include ``eq``,
   ``contains``, ``between``, ``hashes-to``, and ``hashes-like``.

#. Save. To version-control the exact definition, capture it from the CLI and
   commit it into ``dos-persistent-signature.conf``::

      tmsh list security dos dos-signature lab_sig_scripted_flood

Task 2: Approve and activate
----------------------------

#. Open the signature's properties. Set **State** = Mitigate and tick
   **Approved** (Approval State → ``Manually-approved``). Tick **Shareable** if
   other VSs should use it.

#. (Optional, stricter) On ``lab_dos_bados_profile`` enable **Use Approved
   Signatures Only**, so nothing mitigates until you've approved it — the safe
   way to roll signatures out in production.

Task 3: Test the custom signature
---------------------------------

#. From kali (``10.1.10.100``), send traffic that matches the predicates — a
   plain header-less ``curl`` (no User-Agent, method GET, short URI)::

      for i in $(seq 1 200); do
          curl -s -o /dev/null -w "%{http_code}\n" -H "User-Agent;" http://10.1.10.63/
      done

   Matching requests are mitigated per the profile once the attack threshold is
   met. (``-H "User-Agent;"`` strips curl's default UA so the
   ``user_agent_header_exists eq false`` predicate fires.)

#. Confirm the hit and its state::

      tmsh show security dos dos-signature lab_sig_scripted_flood

   Look for a non-zero **Attack Status** / drops.

#. Send a browser-like request (with a normal User-Agent) and confirm it passes
   — the signature targets the attack's shape, not all traffic.

Task 4: Promote a dynamic (BADoS) signature to persistent
---------------------------------------------------------

The other route is to let BADoS find the attack, then keep the signature it
generated.

#. Run the behavioral attack from Lab 2 so BADoS generates dynamic signatures::

      bash ~/lab/scripts/attack/http-flood.sh http://10.1.10.63 60 100

#. On the **Dynamic** tab, review the generated signatures (each expands to show
   its predicate list). Pick an effective one, select it, and click **Make
   Persistent**, then mark it **Approved**. CLI equivalent::

      tmsh list security dos dos-signature { type dynamic }
      tmsh modify security dos dos-signature <HTTPSig...> \
          type persistent shareability-state fully-shareable \
          approval-state manually-approved state mitigate

   A promoted signature keeps ``origin dynamic-bdos`` (vs ``user-defined`` for
   hand-authored), so you can always tell how each one was created.

#. Re-run the attack and confirm the now-persistent signature mitigates
   immediately, without waiting for BADoS to re-learn.

Task 5: Share the signature to another VS
-----------------------------------------

A **Shareable** persistent signature applies to any other protected object whose
DoS profile has signatures enabled — bind the BADoS profile to a second VS and
confirm the same signature mitigates there. A non-shareable signature only
applies to the context that created it.

.. important::

   A persistent signature is a static match — an attacker who changes the
   matched attribute (adds a User-Agent, lengthens the URI) evades it. Use
   persistent signatures to lock in mitigation for a *known* attack shape, and
   keep BADoS running for the adaptive, unknown ones. The two are complementary.

Questions
~~~~~~~~~

- When would you set a signature to Learn Only or Detect Only rather than
  Mitigate — and how does "Use Approved Signatures Only" make rolling one out
  safer?
- Your signature ANDs three predicates. What breaks if you keep only
  ``http.user_agent_header_exists eq false`` — too broad, too narrow, and which
  legitimate clients might it catch?
- A promoted dynamic signature keeps ``origin dynamic-bdos``; a hand-authored one
  is ``user-defined``. Why does that provenance matter when auditing which
  signatures are enforcing, and who changed them?
